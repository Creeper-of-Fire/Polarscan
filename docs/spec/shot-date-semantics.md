## 1. 背景

一张拍立得是**一次瞬时曝光**。它发生在某一个确定时刻，因此有且只有一个拍摄日期。

「跨日拍立得」不是一种类型。一张照片要跨过两个日期，唯一可能是恰好在 `00:00:00`
那一秒——概率为零。早年代码里存在过「跨日拍立得有歧义」这个前提，见 § 4，它是错的。

`Polaroid.shot_date` 记录的就是这一个日期。

## 2. 设计

### 2.1 `shot_date` 是拍摄日期，唯一来源

- **id 里的日期不是契约**。当初批量入库时用它省事而已（也可以整个换成 GUID，行为
  不变），它不承担任何语义，代码**不得解析它**。
- **文件名里的日期是扫描日，不是拍摄日**——拍完过一阵才扫。从文件名推拍摄日是在推
  另一个量，所以**不存在这条兜底**。

### 2.2 候选日是推荐值，不是判断

候选日来自资产所在文件夹的名字（见 § 3），是「可能合理的几个值」。代码**不做选择**。

文件夹名只提供日号。一个文件夹里装了哪些天，不等于这批拍立得是哪天拍的——所以它
只能产生推荐，不能产生结论。

### 2.3 空的时候也不自动填

**候选日永远不得自动写入 `shot_date`，哪怕候选只有一个、哪怕字段是空的。**

自动填会让推算冒充事实：用户看到输入框里有值，无从分辨那是自己填的、还是系统猜的。
这是意义撕裂。

空就是空。

### 2.4 显式手势才写入

候选以按钮 / 日期区呈现，用户显式手势（点击按钮、或把卡片拖入日期区）才填入。
**用户的操作产生用户预期的结果**——这条是 2.3 的
对偶：既然不自动填，就必须让填入这个动作明确可见、可归因于用户。两种手势等价，
均为"用户明确决定"。

### 2.5 有值时不看候选

有值就是有值，没有谁能动它。候选按钮只用于帮助用户在**空值**时做决定，不会去覆盖或
清空已有值。

## 3. 接口契约

| 层 | 导出 | 契约 |
|---|---|---|
| 兼容层 | `parseFolderDays(name)` | 文件夹名 → 候选日数组；不认识则 `null` |
| 通用层 | `parentDirName(path)` | 取父目录名 |
| 通用层 | `collectCandidateDays(assets)` | 一组资产 → 合并去重升序的候选日数组 |

**边界**：通用层不认识任何命名语法，全部外包给兼容层。兼容层是**对个人命名习惯的
适配器，不是项目规则**——可改、可删、可整块替换；将来要大量改命名习惯，只动那一个
文件。**不要**把它写进 spec 当成约定（它本来就不在这里）。

**写入路径**：候选日 → 按钮（`applyDate(d)`）或日期区（拖入）→ `shot_date`。这是唯一一条能写
`shot_date` 的路径，且必须由用户显式手势（点击 / 拖入）触发——[ingest-scan](ingest-scan.md)
的拖入与本条等价。

## 4. 验证

`tests/path_parse_js_test.mjs`：**14/14 通过**（`node --experimental-strip-types --test`）。

### 4.1 三条被否证的旧规则

保留在此，是因为它们都曾以「正确行为」写在代码注释里甚至**被测试钉住**。不记下来，
下一个读到的人会重新发明它们。

**① 「跨日拍立得有歧义 → 候选 ≥2 时强制清空 `shot_date`」**

前提不存在（见 § 1）。实现更糟：`useShotDateResolver` 带 `immediate: true`，打开既有
拍立得就立即清空；而 BenchView 任意字段改动都会 PUT 整个 polaroid，等于把磁盘上已有的
日期静默抹掉。**已删除。**

**② 「id 的日期区间取首日」**

没有任何依据——「取首日」这个规则从未被验证过，是凭空补的默认值。它还给推断出的日期
打上「由 id 推导」的标签展示给用户，等于把猜测包装成事实。**已删除**（`shotDateHint` /
`idDateRange`，浏览页不再显示该标签）。

**③ 「从文件名 `imgYYYYMMDD_` 兜底推断拍摄日」**

文件名是扫描日（§ 2.1）。这条兜底是"解析不出就退而求其次"，但退到的那个量是错的。**已删除**。

### 4.2 测试本身也曾是腐朽的一部分

旧用例 `test('shotDateHint: 取首日')` 把错误规则断言成了正确行为：谁改它谁看到红灯，
于是没人敢动。**规则写错时，把它钉进测试等于给它发免死金牌。** 现已连同实现一起重写。

### 4.3 兼容层语法规则的回归

以下各有专门用例，因为都是曾经错过的：

- `&` 是**离散列出**，不补中间（曾经与 `-` 同路径，凭空造出中间那天）
- `&` 可以连三个以上
- **跨年必须写完整年份**；`2026.12.28-01.03` 拒绝——月变小是跨年信号，但年份不猜
- `-` 是连续区间，逐日包含中间
- 文件名不参与（`collectCandidateDays` 用例显式覆盖）

## 5. 演进约束

- **新增任何拍立得相关路径时，不得存在「推断即写入」**。推断结果只能进按钮。
  任何"聪明一点自动填"的改动都要先问：用户看得出这个值是自己填的还是猜的吗？
- **不得让 id 或文件名参与日期推断**（§ 2.1）。
- 改候选日的来源逻辑 = 改兼容层，其他代码不应跟着动。
